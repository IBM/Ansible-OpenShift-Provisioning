Step 3: Set Variables (host_vars)#

Overview#

  • Similar to the group_vars file, the host_vars files for each LPAR (KVM host) must be filled in.
  • For each KVM host to be acted upon with Ansible, you must have a corresponding host_vars file named <kvm-hostname>.yaml (i.e. ocpz1.yaml, ocpz2.yaml, ocpz3.yaml), so you must copy and rename the template lpar.yaml.template found in the host_vars folder accordingly.
  • Template: lpar.yaml.template is the single template for all LPAR use cases. It replaces the deprecated KVMhostname1-here.yaml.template, KVMhostname2-here.yaml.template and KVMhostname3-here.yaml.template, which will be removed in upcoming PRs. It covers:
    • KVM installation: the LPAR is a KVM host (RHEL + libvirt) that runs the cluster nodes as KVM guests. The file name must match env.z.lpar1.hostname, env.z.lpar2.hostname or env.z.lpar3.hostname. For the second and third KVM host use the secrets vault_lpar2_user_pass / vault_lpar2_root_pass and vault_lpar3_user_pass / vault_lpar3_root_pass instead of the vault_lpar1_* names used in the template.
    • LPAR / ABI installation: the cluster node itself runs in the LPAR. The file name must match the node's vm_name (see Section 8).
    • LPAR creation on DPM: when Ansible creates the LPAR (env.z.lpar1.create: True, role create_lpar), the template defines the DPM partition on the HMC: its IFL and memory (Section 4), NICs (Section 5) and storage groups (Section 6). The CPC must be DPM enabled. For a classic (PR/SM) LPAR that already exists, these items are not required.
    • In the template, items needed only for one case are marked [KVM] or [DPM].
  • The variables marked with an X are required to be filled in. Many values are pre-filled or are optional.
  • Optional values are commented out; in order to use them, remove the # and fill them in.
  • Many of the variables in these host_vars files are only required if you are NOT using pre-existing LPARs with RHEL installed. See the Important Note below this first section for more details.
  • LPAR ABI deployments: The filename of each host_vars file (<vm_name>.yaml) must match the corresponding env.cluster.nodes.control.vm_name[n] or env.cluster.nodes.compute.vm_name[n] value in group_vars/all.yaml. This is not the same as the OCP node hostname (set via env.cluster.nodes.*.hostname[n]). See Section 8 for a full explanation.
  • This is the most important step in the process. Take the time to make sure everything here is correct.
  • Note on YAML syntax: Only the lowest value in each hierarchicy needs to be filled in. For example, at the top of the variables file networking does not need to be filled in, but the hostname does. There are X's where input is required to help you with this.
  • Scroll the table to the right to see examples for each variable.

Important Note#

  • You can skip the rest of the variables on this page IF you are using existing LPAR(s) that has RHEL already installed.
  • If you are installing an LPAR based cluster then the information below must be provided and are not optional. You must create a host file corresponding to each lpar node.
    • Since this is how most production deployments on-prem are done on IBM zSystems, these variables have been marked as optional.
    • With pre-existing LPARs with RHEL installed, you can also skip 1_create_lpar.yaml and 2_create_kvm_host.yaml playbooks. Make sure to still do 0_setup.yaml first though, then skip to 3_setup_kvm_host.yaml
    • In the scenario of lpar based installation you can skip 1_create_lpar.yaml and 2_create_kvm_host.yaml. You can also optionally skip 3_setup_kvm_host.yaml and 4_create_bastion.yaml unless you are planning on having the bastion on the same host.
    • In case of lpar based installation one is expected to have a tessia live disk accessible by the lpar nodes for network boot. The details of which are to be filled in section #7 below. The steps to create a tessia livedisk can be found here.

5 - Networking#

The network of the LPAR is activated at boot with the kernel parameter rd.znet=qeth,<read>,<write>,<data>,layer2=1,portno=<port>, which is built from card1. Therefore card1.dev_num and card1.port are required for every LPAR installation (KVM host or LPAR / ABI node). card1.name and card1.adapter are only needed to create the NIC in the HMC partition when Ansible creates the LPAR (DPM).

Variable Name Description Example
lpar.networking.subnet_cidr The same value as the above variable but in Classless Inter-Domain Routing (CIDR) notation. Used in the ip= boot parameter of the KVM host. 23
lpar.networking.nic.osa_card.dev_num (Optional) Required only when network mode is HIPERSOCKET The device numbers of the OSA Network Interface Card (NIC) as a comma separated string. When defined, it is passed as the network device to the HMC load. 0.0.1100,0.0.1101,0.0.1102
lpar.networking.nic.card1.name (DPM creation only) The logical name of the Network Interface Card (NIC) within the HMC. An arbitrary value that is human-readable that points to the NIC. For a KVM host with two NICs it is also used as bond slave interface name. SYS-NIC-01
lpar.networking.nic.card1.adapter (DPM creation only) The physical adapter name reference to the logical adapter for the LPAR. 10Gb-A
lpar.networking.nic.card1.port (Required) The port number for the NIC. Used as portno= in rd.znet. 0
lpar.networking.nic.card1.dev_num (Required) The device number of the NIC. The format depends on the use case, see the note below the table. 0x0100 or 0.0.1100,0.0.1101,0.0.1102
lpar.networking.nic.card2.name (Optional) The logical name of a second Network Interface Card (NIC) within the HMC. An arbitrary value that is human-readable that points to the NIC. SYS-NIC-02
lpar.networking.nic.card2.adapter (Optional) The physical adapter name of a second NIC. 10Gb-B
lpar.networking.nic.card2.port (Optional) The port number for a second NIC. 1
lpar.networking.nic.card2.dev_num (Optional) The logical device number for a second NIC. Same format rules as card1.dev_num for a KVM host / LPAR creation (hex integer). 0x0001

Format of card1.dev_num: * LPAR / ABI node (boot_LPAR, boot_LPAR_abi) and network mode hipersocket: the three CCW devices (read, write, data) as one comma separated string, e.g. 0.0.1100,0.0.1101,0.0.1102. * KVM host installation (update_cfgs) and LPAR creation (create_lpar): only the first device number is given. The write and data devices are derived as +1 and +2. The value is evaluated as an integer and converted to 4 hex digits, so use unquoted YAML hex notation, e.g. 0x1100 (becomes 1100, 1101, 1102).

8 - LPAR ABI: vm_name, hostname, and mac explained#

This section explains three variables that are distinct but easily confused when deploying an Agent-Based Installer (ABI) cluster directly on bare-metal LPARs.

vm_name vs hostname#

Variable Where set Purpose
env.cluster.nodes.*.vm_name[n] group_vars/all.yaml Sections 8 & 9 Filename stem of host_vars/<vm_name>.yaml. Used by boot_LPAR_abi to load HMC/LPAR credentials and livedisk settings, and by agent-config.yaml.j2 to look up FCP rootDeviceHints.
env.cluster.nodes.*.hostname[n] group_vars/all.yaml Sections 8 & 9 Short OCP node hostname. Combined with metadata_name and base_domain to form the FQDN written as the hostname: field in agent-config.yaml (e.g. control-01.ocpz.example.com). Also used for DNS A/PTR records and HAProxy server lines by the setup_bastion_services role.

On KVM deployments vm_name and hostname are typically the same value because the libvirt VM name and the OCP hostname are set identically by convention.

On LPAR ABI deployments they are independent: - vm_name identifies the LPAR's host_vars file (e.g. lpar-node-1 → host_vars/lpar-node-1.yaml). It is the HMC/CPC identity. - hostname is the OCP node short name (e.g. control-01). It is combined with metadata_name and base_domain to produce the FQDN written into agent-config.yaml (e.g. control-01.<metadata_name>.<base_domain>). This FQDN is what OpenShift registers as the node name, so it must be DNS-resolvable.

Example (group_vars/all.yaml):

env:
  cluster:
    nodes:
      control:
        vm_name:   # host_vars filenames — match your LPAR names in HMC
          - lpar-cpc1-01
          - lpar-cpc1-02
          - lpar-cpc1-03
        hostname:  # OCP node hostnames — used for DNS and HAProxy
          - control-01
          - control-02
          - control-03

With the above, you must have host_vars/lpar-cpc1-01.yaml, host_vars/lpar-cpc1-02.yaml, host_vars/lpar-cpc1-03.yaml. DNS will be configured for control-01.<metadata_name>.<base_domain>, and agent-config.yaml will contain hostname: control-01.<metadata_name>.<base_domain> — the FQDN that OpenShift registers as the node name (visible in oc get nodes).

mac is required for LPAR ABI#

The env.cluster.nodes.*.mac[n] variable is required for LPAR ABI deployments. It is used in agent-config.yaml.j2 for two purposes: 1. The interfaces[].macAddress: field — tells the agent which NIC to configure with the static IP. 2. The networkConfig.interfaces[].mac-address: NMState field — configures the interface for static IP assignment.

Without this value the agent cannot match the correct network interface and the node will not join the cluster.

MAC Address Determination by Environment and Adapter Type#

  • RoCE Adapters: Use the actual physical MAC address assigned to the RoCE card.
  • DPM Mode: Use the MAC address configured/assigned to the network adapter in DPM.
  • Non-DPM Mode with Non-RoCE Adapters (e.g., OSA-Express / HiperSockets): Non-DPM LPARs using OSA or HiperSockets in Layer 2 mode do not have a fixed permanent MAC address and the Linux kernel generates a random MAC address on every boot by default. For these environments, specify a randomly generated MAC address (e.g., 52:54:00:xx:yy:zz or 02:xx:yy:zz:aa:bb using valid unicast hex bytes) in env.cluster.nodes.*.mac in group_vars/all.yaml. During LPAR boot, the boot_LPAR_abi role writes this MAC into the boot parameter file (genericdvd.prm) via dracut's ip=...::<mac> parameter, which forces the kernel to assign this specified MAC to the LPAR interface so that it matches what agent-config.yaml expects.

LPAR Load Status Timeout (Optional)#

By default, the HMC status wait timeout is set to 300 seconds (overriding the upstream zhmcclient default of 60 seconds). It applies when the LPAR is deactivated before an ABI boot (boot_LPAR_abi) and when DASD or SCSI live disks are loaded. You can customize this timeout per node or globally: - Per node in host_vars/<node>.yaml: lpar.livedisk.load_status_timeout: 300 - Globally in group_vars/all.yaml: env.lpar_load_status_timeout: 300

Precedence: lpar.livedisk.load_status_timeout, then lpar.load_status_timeout (older name, still honoured), then env.lpar_load_status_timeout, then 300.

LPAR Stop Method (Optional)#

Before an ABI boot, boot_LPAR_abi stops an LPAR that is still running (status operating or exceptions) when deactivate_lpar_before_boot is true (default). By default it uses the HMC Deactivate Logical Partition operation (deactivate), which can take several minutes on a node that was running OpenShift. If you are reinstalling and do not need the node to shut down cleanly, set the method to reset_clear (HMC Reset Clear, which resets the LPAR without waiting for the OS) to save that time: - Per node in host_vars/<node>.yaml: lpar.livedisk.deactivate_method: reset_clear - Globally in group_vars/all.yaml: env.lpar_deactivate_method: reset_clear

Precedence: lpar.livedisk.deactivate_method, then env.lpar_deactivate_method, then deactivate. Allowed values are deactivate and reset_clear; anything else fails the play. Memory and processors are reset, so use reset_clear only when the contents of the LPAR may be discarded. The LPAR is then activated and loaded as usual.
